### D63: Underwater Glider Sawtooth Profiling Kinematics & Vertical Exaggeration (Phase 12)
- **Context:** Underwater gliders profile via variable buoyancy propulsion, navigating cyclic dive/climb paths (sawtooth / yo-yo trajectories) typically from 0m to 1,000m depth across hundreds of kilometres. Direct spherical scaling ($1,000\text{m} / 6,371,000\text{m} \approx 0.000157$) makes vertical dives invisible on a globe of radius $R=100.0$.
- **Decision:** Adopt Handbook H23 depth exaggeration factor ($E = 30$), scaling visual depth radius according to $r = R - \text{depth} \times \text{scale}$, where $\text{scale} = 0.000471$. Surface waypoints anchor at $R=100.0$; deep dive inflections (1,000m) retract inwards to $r=99.529$. This cleanly differentiates surface navigation from subsurface water column penetration while preserving geographic lat/lon positioning.

### D64: Discontinuity & QC Gap Segmentation Architecture (Phase 12)
- **Context:** Glider sensor transmissions may suffer telemetry dropouts, sensor aborts, missing depth measurements, or bad QC flags (flags 3, 4). Drawing continuous linear interpolation across these gaps introduces false oceanographic data bridging.
- **Decision:** Enforce strict gap segmentation in `gliderTransects.js`. Missing depth values (`depth === null`), bad QC flags (flags 3, 4), or temporal gaps exceeding 12 hours split the trajectory into disconnected Three.js `Line` segments. No line geometry is generated across invalid or missing data points.

### D65: Glider Surfacing GPS Beacons, Inflection Anchors, and Head Beacon (Phase 12)
- **Context:** Users require immediate visual distinction between glider surface events (satellite telemetry & GPS fixes) and subsurface turnarounds.
- **Decision:** Implement dedicated Three.js markers:
  - Surface GPS Beacons ($z=0$): Rendered as prominent cyan spheres ($r=0.45$) on the sea surface.
  - Dive Bottom Inflection Anchors: Rendered at maximum dive cycle depths as gold/amber anchors ($r=0.35$).
  - Glider Head Marker: Rendered at the latest mission waypoint as a distinctive navigational beacon with pulsing orientation.

### D66: Earth Line-of-Sight Occlusion & Drag-vs-Click Selection (Phase 12)
- **Context:** Waypoints on the far side of the Earth globe must not render on top of near-side ocean or register false raycast click events.
- **Decision:** Apply Earth occlusion calculations (camera dot product $\mathbf{P} \cdot \mathbf{C} > 0$) to filter out occluded beacons and prevent raycast picking through the solid planet. Maintain drag-vs-click discrimination ($\le 4\text{px}$) to avoid unintentional platform selection during globe orbit maneuvers.

### D67: Multi-Sensor Concurrency & ProfileModal Integration (Phase 12)
- **Context:** Argo float point markers, glider 3D sawtooth transects, and ROMS ocean current streamlines must operate concurrently without DOM, WebGL, or state collisions.
- **Decision:** Unify sensor inspection in `ProfileModal.jsx` using `platform_type` tags (`ARGO FLOAT` vs `GLIDER TRANSECT`). When a glider mission is selected, the modal presents vertical CTD curves (Temperature, Salinity) and T-S correlation diagrams with UNESCO EOS-80 isopycnals. Multi-sensor WebGL rendering maintains 165 FPS (>60 FPS requirement).

### D68: Collocation Sign Convention (Phase 13)
- **Context:** Handbook p. 11 uses ambiguous "model minus observed" phrasing in one section, while pp. 5-6 define Δ = MODEL − OBSERVED explicitly. The conflict is irreconcilable without a tiebreaker.
- **Decision:** Adopt the explicit two-example definition from pp. 5-6: $\Delta = \text{MODEL} - \text{OBSERVED}$. Negative Δ indicates model under-prediction; positive Δ indicates model over-prediction. Verified test case: model=18.5, observed=19.1 → Δ = −0.6 (under-prediction); model=19.1, observed=18.5 → Δ = +0.6 (over-prediction). Recorded in D05 (Phase 1) and enforced in D68 (Phase 13 implementation).

### D69: Trilinear Interpolation over cKDTree (Phase 13)
- **Context:** The collocation engine must spatially interpolate model values to arbitrary (lat, lon, depth) observation coordinates. Two approaches were considered: trilinear interpolation on the rectilinear grid, or approximate nearest-neighbour search with `scipy.spatial.cKDTree`.
- **Decision:** Implement exact trilinear interpolation across bounding 8-corner grid cells. Rationale: (1) the model grid is a regular rectilinear 4D array — bounding indices are found in O(log N) via `np.searchsorted`, no tree required; (2) trilinear exactly reproduces affine fields, enabling analytical verification to machine precision (<10⁻⁴ error); (3) cKDTree nearest-neighbour introduces systematic bias at grid-cell midpoints. No external SciPy spatial dependency added.

### D70: Masked Array Land Detection (Phase 13)
- **Context:** The synthetic NetCDF file stores ocean/land discrimination via `numpy.ma.MaskedArray` with `_FillValue = −999.0`. Early implementations checked `dataset.variables['temperature'][:].mask` directly, which failed because `mask` is `False` (scalar) when no values are masked, not an array.
- **Decision:** Use `np.ma.is_masked(val)` on individually extracted grid corner values, combined with `val == −999.0` sentinel fallback. This is safe for both scalar and array masked values and handles the specific NetCDF structure generated by `generate_synthetic_data.py`.

### D71: Real Sample Domain Correction (Phase 13)
- **Context:** `ARGO_2902210_REAL` was stored with `lat = −11.25` (South Indian Ocean, outside 0°–25°N domain). `GLIDER_REAL_INCOIS_SG02` was stored with `lon = 76.4` which lands on a masked Indian subcontinent grid cell. Both caused collocation endpoint 404/422 errors during acceptance testing.
- **Decision:** Update `real_argo_sample.json` to `lat = 11.25` (Lakshadweep Sea) and `real_glider_sample.json` to `lon = 72.4` (open Arabian Sea, Lakshadweep region). Both remain realistic INCOIS deployment positions. Documented as sample data editorial correction, not scientific data alteration.

### D72: ComparisonPanel Live Collocation Upgrade (Phase 13)
- **Context:** `ComparisonPanel.jsx` previously showed static placeholder "—" values for model difference and health, deferred from Phase 11 by explicit Phase 13 Contract comment.
- **Decision:** Replace the placeholder with live collocation metrics fetched from `/api/collocation/profile/{id}` when an Argo float is selected. Difference metric displays computed Temperature Bias (°C); Model Health Assessment classifies RMSE into EXCELLENT (<0.3°C), ACCEPTABLE (0.3-1.0°C), or REQUIRES_CALIBRATION (>1.0°C). `ComparisonPanel` and `ProfileModal` independently fetch collocation — acceptable redundancy because both components may be visible simultaneously and have different update lifecycles.

### D73: Diverging Color Palette for Difference Field & Heatmap (Phase 14)
- **Context:** Residuals ($\Delta = \text{MODEL} - \text{OBSERVED}$) represent positive and negative deviations that must be visually distinguishable at a glance on the 3D globe.
- **Decision:** Implement a diverging color palette centered at zero:
  - $\Delta < 0$ (model under-prediction): Deep sky blue to cyan (`#0284c7` to `#38bdf8`).
  - $|\Delta| < 0.05$ (near-zero residual): Light neutral white/slate (`#f8fafc`).
  - $\Delta > 0$ (model over-prediction): Amber to crimson red (`#fbbf24` to `#ef4444`).
  Temperature (°C) and Salinity (PSU) scales are kept strictly separated and never mixed.

### D74: Sparse Observations Policy & Defined Support Radius (Phase 14)
- **Context:** Ocean in-situ observations (Argo floats and gliders) are sparse point measurements. Rendering a full continuous volume heatmap across the entire ocean would mislead users into believing continuous observations exist where none were taken.
- **Decision:** Strictly enforce a sparse observation policy: residuals are rendered exclusively at directly observed $(t, \text{lat}, \text{lon}, z)$ coordinates as 3D Three.js `InstancedMesh` spheres. A documented support radius of ~55 km (one 0.5° model grid cell) is specified; no spatial interpolation or extrapolation is performed beyond this support radius. Coverage holes are explicitly reported in the API (`has_data = false`) and an honest disclaimer is rendered in the UI.

### D75: Configurable Threshold Discrepancy Alerts vs Hazard Claims (Phase 14)
- **Context:** Discrepancies between numerical simulations and in-situ CTD profiles occur due to model discretization, sub-mesoscale eddies, or sensor bias. Handbook warns against fabricated hazard claims.
- **Decision:** Implement configurable anomaly thresholds (default 0.5°C / 0.1 PSU). Any level with $|\Delta| \ge \text{threshold}$ is classified strictly as a `"Model-observation discrepancy"` — never as a "hazard", "warning", or "physical alert". Every alert in `ComparisonPanel` is traceable: clicking an alert item navigates directly to the source platform's CTD curves in `ProfileModal`.

### D76: Deferral of 88.4% Percentage Health Score Widget (Phase 14)
- **Context:** Handbook p. 11 illustrates an "88.4% Model Health" badge in wireframes without providing any mathematical definition, reference scale, or empirical grounding (Conflict C05 / D07).
- **Decision:** Maintain explicit deferral of the percentage score per D07. Present scientifically grounded error metrics instead: mean Bias, MAE, RMSE, valid matched pair counts, and threshold discrepancy counts. The API returns `health_score_status: "DEFERRED (D07)"` ensuring complete transparency.

### D77: Grounded Deterministic AI Assistant Architecture (Phase 15)
- **Context:** Large Language Models (LLMs) calling external cloud APIs introduce substantial network latency (>2-5s), risk catastrophic scientific hallucination during naval operations, incur per-token recurring costs, and fail in air-gapped defense or research vessel networks.
- **Decision:** Implement a deterministic, grounded ocean intelligence engine (`backend/app/services/ai_assistant.py`). Queries are classified into specialized numerical evaluation pipelines (`LARGEST_RESIDUAL`, `OBSERVATION_COVERAGE`, `DOMAIN_EXTREMES`, `PLATFORM_SUMMARY`). The engine evaluates live NetCDF arrays and in-situ collocation databases directly in Python using NumPy and SciPy. Responses are formatted deterministically with structured supporting metrics, mathematical units, and data provenance. No external cloud API keys are required.

### D78: Multi-Layer Adversarial Prompt Injection Defense (Phase 15)
- **Context:** User inputs entered into conversational fields could contain jailbreak attempts, system prompt overrides, or attempts to extract system credentials (`"Ignore previous instructions"`, `"Reveal secret keys"`, etc.).
- **Decision:** Implement regex-based boundary sanitation (`ADVERSARIAL_PATTERNS`). Any input matching prompt injection or system override signatures is neutralized immediately, returning an informative grounded error explaining that the AI Assistant is strictly restricted to oceanographic data synthesis within the North Indian Ocean domain.

### D79: Sub-200ms Cached Metric Evaluation for Assistant Queries (Phase 15)
- **Context:** Operational operators require immediate answers during maritime briefings. Handbook specifies sub-second response times, and Phase 15 acceptance criteria target sub-200ms latency.
- **Decision:** Cache global domain extrema, active platform counts, and collocation residuals in memory on service initialization with periodic background refresh. Heavy array traversals are pre-aggregated, allowing complex analytical queries (e.g., maximum temperature discrepancy across all platforms) to resolve in under 150ms (measured average: 141.36ms).

### D80: Multi-Stage Production Containerization and Air-Gapped Deployment (Phase 15)
- **Context:** Deployment at INCOIS or on research vessels requires seamless containerization with zero external CDN dependencies and reliable orchestration.
- **Decision:** Provide a standardized `docker-compose.yml` orchestrating:
  1. `samudra-3d-backend`: Python 3.11-slim container with pre-installed HDF5/NetCDF4 dependencies, running FastAPI via Uvicorn on port 8000 with healthcheck probes.
  2. `samudra-3d-frontend`: Multi-stage Docker build (Node 20 Alpine builder -> Nginx Alpine server) serving optimized static assets on port 80/3000 with reverse proxy for `/api/` routing.
  Both containers run self-contained without internet egress.
