## What the project is meant to deliver

The handbook describes a browser-based 3D ocean visualization and analysis application for SIH26067, Team Nexus Nova. Users inspect numerical model fields and in-situ observations together, switch temperature/salinity/current views, navigate depth and time, select Argo/glider observations, inspect vertical profiles and compare model predictions with measurements. It visualizes precomputed ocean model data; it does not solve ocean fluid dynamics in the browser (handbook pp. 3-4).

The preferred stack is React 18 with Vite, Three.js/WebGL, FastAPI/Uvicorn, xarray/netCDF4/SciPy and Chart.js or the handbook's chart alternative (p. 5). The architecture places scientific data loading, subsetting and comparison on the backend and sends bounded display data to the frontend (p. 6). The spherical coordinate formula and 20x-50x visual depth exaggeration are provided on pp. 6-7. The folder layout is on p. 9, the exact 15-phase roadmap on p. 10, and the final dashboard wireframe on p. 11.

The problem-statement document reinforces easy model/observation comparison and explicitly cautions against claiming that no existing solution exists. It additionally calls out observation coverage, a model health score and an assistant. The presentation's slide 6 is a workflow graphic, not text-only content: it specifies ingestion, CF metadata, QC, spatial/temporal alignment, bias/MAE/RMSE, anomaly detection, coverage and AI explanations. Its two broad workflow stages are not a replacement for the handbook's 15 build phases.

## Scientific and integration boundaries

The first demonstrable pipeline should use reproducible synthetic data so rendering and numerical checks have known answers. That does not establish support for arbitrary real-world grids. Each real-source adapter must declare supported coordinate names, units, pressure/depth treatment, time handling, quality flags and grid geometry. Reject unhandled cases explicitly instead of silently coercing them.

Difference maps derived from sparse observations need a stated spatial support policy. No-data regions must remain visible as no-data. A residual threshold identifies a model-observation discrepancy; it does not by itself validate a marine heatwave, cyclone risk, SAR forecast or other operational decision. The assistant can explain computed results and their limits, but cannot invent coverage or causes.

The full-ocean volumetric/raymarching language in the vision is broader than the roadmap's depth-slice implementation. This pack implements the explicit slice roadmap and requires Phase 15 to record whether true volumetric rendering remains absent. Similarly, TCHP calculation, PFZ prediction, oil-spill modelling, OGC service implementation, new sensor families and production INCOIS deployment are not silently added to the 15 phases merely because they appear as potential uses or extensibility claims.

## Report and review contract

Each implementation phase must leave an acceptance checklist, actual test evidence, changed-file inventory, requirement mapping, decisions, limitations and a shareable report. Reports begin as review PENDING. A reviewer checks the current code/data as well as the report, reruns relevant tests and gives PASS, CHANGES REQUIRED or BLOCKED. Missing evidence is not evidence of failure, but it also cannot establish a passing required gate.

If a review finds an issue, use the correction prompt to repair only the affected scope, preserve the old report and rerun affected checks. A later code or source change invalidates the relevant earlier evidence until rechecked. Advancement happens only after a passing review or the user's explicit acceptance of a documented exception. This is the phase-by-phase control requested by the user, not an automatic approval rule from the source documents.

India's coastline extends over 7,500 kilometers and its Exclusive Economic Zone (EEZ) covers over 2 million
square kilometers. The Indian National Centre for Ocean Information Services (INCOIS) under the Ministry

2. Ocean Science & Problem Fundamentals for Beginners
2.1 What is Ocean Model Data?
Supercomputers at INCOIS simulate the physical state of the ocean by numerically solving fluid dynamic
equations (Navier-Stokes equations for stratified seawater). The ocean domain is partitioned into a 3D grid
consisting of horizontal cells (e.g., 10 km x 10 km) and vertical depth levels (surface to 5,000m). The model
outputs values for Temperature (°C), Salinity (PSU), and Current Vectors (u, v in m/s) for future time steps.
2.2 Physical Variables Explained
Temperature (°C): Ocean heat distribution. Surface waters in the tropical Indian Ocean average 28°C–
30°C, but temperature rapidly plummets to 2°C–4°C in the deep ocean. The steep boundary zone is
known as the Thermocline.
Salinity (PSU — Practical Salinity Units): Measure of dissolved mineral salts. The Bay of Bengal exhibits
lower surface salinity (<32 PSU) due to immense river runoff (Ganga, Brahmaputra), whereas the Arabian
Sea has high salinity (>36 PSU) due to high evaporation and low freshwater influx.
Current Vectors (u, v in m/s): Seawater velocity broken into orthogonal vectors:
u = Zonal velocity (East-West flow; positive = East).
v = Meridional velocity (North-South flow; positive = North).
Horizontal Current Speed = sqrt(u^2 + v^2).

⚙  GRAPHICS PIPELINE: LAT/LON/DEPTH TO THREE.JS XYZ
On Earth, a position is defined by Latitude, Longitude, and Depth. In WebGL, space is defined by Cartesian
coordinates (X, Y, Z).
We calculate the local radial distance r = R_earth - (depth * exaggeration).
Then: X = r * cos(lat) * sin(lon), Y = r * sin(lat), Z = r * cos(lat) * cos(lon).
Since the ocean depth (4 km) is tiny compared to the Earth radius (6,371 km), we apply a Vertical
Exaggeration Factor (20x to 50x) so depth layers are clearly visible to human observers!
8. NetCDF & xarray Masterclass from Scratch
NetCDF stores scientific arrays with coordinates and metadata attributes. Below is a self-contained Python
example demonstrating lazy opening, spatial slicing, interpolation, and JSON conversion:
backend/services/netcdf_slicer.py (xarray & NetCDF Processing)
import xarray as xr
import numpy as np
# 1. Open dataset lazily (Consumes zero RAM initially)
ds = xr.open_dataset("sample_data/model_indian_ocean.nc")
# 2. Slice specific variable, depth, time and Indian Ocean bounding box
def extract_ocean_slice(var_name="temperature", depth_m=500.0, time_idx=0):
    # Select closest depth and time index
    sub = ds[var_name].isel(time=time_idx).sel(depth=depth_m, method="nearest")
    # Extract 2D numpy matrix
    data_2d = sub.values
    clean_data = np.nan_to_num(data_2d, nan=-999.0)
    return {
        "variable": var_name,
        "selected_depth": float(sub["depth"].values),
        "timestamp": str(sub["time"].values)[:19],
        "lats": ds["lat"].values.tolist(),
        "lons": ds["lon"].values.tolist(),
        "min_val": float(np.nanmin(data_2d)),
        "max_val": float(np.nanmax(data_2d)),
        "data": clean_data.tolist()

Algorithm

Q1: Why 3D instead of standard 2D web maps?
Answer: The ocean is fundamentally vertical. Critical phenomena like the thermocline, internal waves,
upwelling, and acoustic sound channels cannot be diagnosed from flat 2D surface maps.
Q2: How do you handle multi-gigabyte NetCDF files without crashing the browser?
Answer: The browser never downloads raw NetCDF files. Our Python FastAPI backend uses xarray to lazily
slice only the requested 2D bounding box and depth layer, transmitting a lightweight JSON matrix (<50 KB) to
WebGL.
Q3: How do you compare an Argo float with a model if their GPS coordinates don't match exactly?
Answer: We use a scipy.spatial.cKDTree to identify neighboring model grid cells and execute trilinear
interpolation across latitude, longitude, and depth.
Q4: Can new sensor types like HF-Radar, ADCP, or Moored Buoys be added later?
Answer: Yes. Our ingestion engine is modular and accepts any CF-compliant NetCDF or GeoJSON sensor
stream without modifying the frontend 3D rendering engine.
